# 同じ評価応答から Workflow を修正する比較

取消通知、欠品引当、公開承認の3課題で、前回の比較に保存したモデルの評価応答を12件使った。各応答を2条件に分け、GPT-6 Luna（low）の作成担当を独立に1回ずつ実行した。作成担当の指示、元の Workflow、確定条件、出力形式を揃えた。各条件で、要修正60行・正常36行の計96行を採点した。

素通し側は評価の生応答を渡した。検証側は同じ応答を現在の Evaluator に再生し、Collaboration の実装を経由して、評価が完了した場合に指摘を渡した。未完了時は元資料だけで修正した。再生した全応答について、過去の実験と資料・出力スキーマ・検証後の指摘・範囲判定が一致した。現在の評価指示には過去の実験以降の変更がある。評価応答は固定し、作成担当の推論だけを新たに行った。

実際の Collaboration の引継ぎを使い、作成担当の出力は両条件共通の試験用スキーマで行ごとの値と保留を受け取った。返された値を隔離した Workflow JSON に書き込み、ほかの欄が変わっていないことを照合した。正解表は作成担当へ渡さず、保存された修正版を採点した。欠品引当ではロットの並び順だけの違いは同じ値として扱った。

| 指標 | 生応答を渡す | Evaluator 検証後に渡す |
| --- | ---: | ---: |
| 正しく直した行（返却値を採用） | 59/60 | 58/60 |
| 正常なのに値を変えた行 | 0/36 | 1/36 |
| 全行が正しくなった試行（返却値を採用） | 11/12 | 9/12 |
| 正しい修正値を返しつつ、作成担当が保留とした行 | 4 | 0 |
| 保留行を元の値に戻した場合の正しい修正 | 55/60 | 58/60 |
| 全行が正しくなった試行（保留は変更しない） | 10/12 | 9/12 |
| 評価で正しい値が出たが作成担当に届かなかった行 | — | 4 |
| そのうち修正版でも未修正だった行 | — | 0 |

検証側で届かなかった4行は、欠品引当の同じ1試行に集中した。3行は依存の照合で未確認。1行は行単位で確認されていたが、評価全体が未完了のため指摘を渡さなかった。作成担当は元資料から4行とも正しく直した。

作成担当の保留4行は、素通し側の欠品引当の別の1試行に集中した。値も説明も修正を支持していたが、出力に保留と書かれていた。返却値と保留のどちらを優先するかで修正数が変わるため、両方を集計した。

取消通知では、受領が締切後の失敗ログを除外する必要があった。検証済み側の1試行では、そのログを適用した評価結果が位置・比較・依存の検証を通り、作成担当も同じ理由で誤った現行値を維持した。同じ応答を受けた素通し側は受領時刻を見直し、正しく修正した。別の取消通知試行では検証側だけが修正できた行と、素通し側だけが修正できた行が1行ずつあった。公開承認では検証側だけが正常な P-08 を誤って変更した。

この比較では、Evaluator で検証しても正常行の誤変更は減らず、全行が正しくなる試行も増えなかった。保留を厳守する集計では修正行が3行増えたが、保留と値が矛盾する単一試行に依存する。この成績を専用プロジェクトの継続理由とするには弱い。既存の決定的な検証は、必要になった連携で利用できる。
