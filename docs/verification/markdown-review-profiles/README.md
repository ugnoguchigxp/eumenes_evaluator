# Markdown で Quick の指摘対象を切り替える設計案

現行の `code-correctness` は、変更が導入した具体的な不具合を報告するよう先に指示します。`skillMarkdown` は既存の評価基準を補う位置づけです。特定の観点だけを扱うには、候補を探す段階と、報告する候補を決める段階の両方で Markdown の採用基準を使います。

[試作で使ったモデル指示](quick-profile-system.md)では、固定の不具合レビュー基準を、Markdown に指摘の対象・採否・優先順位を委ねる指示に差し替えました。`focus` で依頼ごとの着眼点を絞れます。今回の版に対する確定条件も照合し、根拠のある違反は Markdown の観点外でも報告します。適用範囲、資料の版と位置、出力形式、入力上限、権限は Evaluator の契約で管理します。固定資料内の命令文は資料として扱います。

[コード品質用 Markdown](../../../examples/skills/code-quality-review/SKILL.md) は機能上の誤り、失敗時の状態、保守作業で生じる具体的な不整合を採用します。[防御的セキュリティ用 Markdown](../../../examples/skills/defensive-security-review/SKILL.md) は、権限、公開範囲、機密性への影響が資料から説明できる候補を採用します。どちらも、変更行と発生条件から影響までをつなぐ処理を既存の `primary` と `evidence` に引用します。

製品に入れる場合は、明示的に選べるコード用の `code-profile` rubric を追加する案です。この rubric では空白以外の `skillMarkdown` を必須とし、既存の `code-correctness` と `code-general` は従来の意味で使えます。呼び出し元は担当に応じて Markdown を渡します。Evaluator は共通の指示で意味を読み取らせ、Quick のモデル呼び出しは1回です。観点の追加に合わせた専用分岐は不要です。

現行の機械検証は、指定された資料 ID と位置が実在し、主根拠が対象範囲内にあることを確認します。引用行だけで主張が成立するかは、今回の比較で別途照合しました。製品に組み込む前に、該当問題がない差分、観点が重なる差分、資料不足、確定条件が観点をまたぐ場合、資料本文に指示が含まれる場合を追加で確認します。

## 比較方法

コード品質の問題と公開範囲の問題を一つずつ含む合成差分を2件用意しました。領収書は数量を反映しない合計とスタッフ用メモの顧客向け出力、エクスポートは保存前の完了状態と非公開連絡先の活動記録への混入です。2差分 × 2つの Markdown × 4方式 × 3回で48試行です。すべての方式で同じ固定資料、同じ Markdown、同じ `focus`、同じモデルと推論強度、同じ出力トークン上限を使いました。

現行 Quick と試作 Quick は Evaluator の既存 API と検証を通し、試作では試験用接続でモデル指示を差し替えました。素の LLM には短いレビュー依頼と同じ資料を直接渡し、既存 JSON スキーマを指定する条件と自由記述の条件を設けました。両条件とも Evaluator に応答を渡さず採点しました。採点では、狙った観点の検出、引用行の充足、別観点の指摘、別観点への補足の言及を数えました。条件名を伏せ、自由記述は文章中の引用を照合しました。

## 実モデル比較

モデルは `gpt-6-luna`、推論強度は `medium`。全48試行を同じモデル API に直接接続して実行し、下表はその結果です。先行の Codex CLI 比較では自由記述の1試行が固定資料にない環境指示に言及したため、モデル API で全条件を測り直しました。

| 方式 | 狙った既知問題を検出 | うち引用行で裏づけあり | 別観点の指摘 | 別観点への補足言及 | 位置不備で除外 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 現行 Quick | 11/12 | 10/12 | 1 | 0 | 1 |
| 試作 Quick | 12/12 | 12/12 | 0 | 0 | 0 |
| 素の LLM・同じ JSON スキーマ | 12/12 | 12/12 | 0 | 0 | — |
| 素の LLM・自由記述 | 12/12 | 12/12 | 0 | 4 | — |

試作 Quick は、コード品質では数量計算と完了状態、セキュリティでは社内メモと非公開連絡先の公開範囲を、各観点で6/6件報告しました。現行 Quick ではセキュリティの試行に完了状態の指摘も1件入りました。また、別の試行で連絡先の指摘が存在しない資料 ID を参照し、既存の検証が除外しました。現行 Quick で保持されたコード品質の指摘のうち1件は、アーカイブ欠落時のエラーに加えて、資料からは確認できない「未完成のアーカイブを返す」可能性も挙げていたため、引用で裏づけられた件数から外しました。

同じ Markdown と JSON スキーマを直接モデルに渡した方式も、この2差分では試作 Quick と同じ件数でした。今回確認した Evaluator の役割は、資料位置と出力の契約を機械的に検証することです。検出力の差を測るには、今回より広い資料から複数箇所の因果を追う差分で比較する必要があります。

試作は試験用接続に限り、製品 API と実行経路は編集していません。固定モデルで入力を照合し、`bun run verify` の63件が通過しました。入力・応答・採点はローカルの `verification-runs/markdown-review-profiles.ACvdfq/api/` にあります。
